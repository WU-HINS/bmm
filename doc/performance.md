# 性能压测报告

> 被测版本：`7103806`（含健康检查端点）→ 本文优化后基线
> 压测时间：单机闭环压测，3 轮取中位数
> 复现：`node bench/seed.mjs` + `node bench/run.mjs --server-pid <pid>`

---

## 0. 结论

1. **公开页面的瓶颈是渲染与序列化，不是数据库**：首页单请求 CPU 约 265ms，其中数据库只占 13.8ms（5%）。
2. **首屏条目数是最大杠杆**：默认页大小 240 → 60 后，首页单请求 CPU 265ms → 90~114ms（**-57%~-66%**），HTML/RSC 体积 894KB → 306KB（**-66%**），单副本吞吐 4.3 → 8.8~12.3 RPS（**+105%~+186%**）。
3. **Node 单进程是硬顶**：所有场景 CPU 占用稳定在 ~1.0~1.15 核，单副本 ≈ 10~13 RPS（首页）。**扩容靠多副本**，不是加并发。
4. **一个路由级重定向的代价被严重低估**：`/tags` 走页面内 `redirect()` 时每请求要付出 35.6ms CPU（整页 layout 渲染），改到 `next.config` 的 `redirects()` 后 **31.8 → 2554 RPS（80×）**，CPU 降到采样精度以下。
5. 用户空间页面本来就轻（45~57ms CPU/req，20~27 RPS），无需优化。

## 3. 瓶颈定位

### 3.1 数据库只占 5%

在 perf.db 上直接调用 controller（不经过 HTTP）：

| 调用 | 平均耗时 |
| --- | --- |
| `PublicTagController.getAll()`（60 个标签） | ~0.00 ms |
| `PublicBookmarkController.total()` | 0.23 ms |
| `findMany()` 240 条 + 关联标签 | **13.84 ms** |
| `findMany({ limit: 60 })` | 4.79 ms |
| `findMany({ limit: 24 })` | 3.71 ms |

查询计划（`ORDER BY updatedAt DESC LIMIT 240`）：

```
SCAN publicBookmarks
USE TEMP B-TREE FOR ORDER BY
```

建 `updatedAt` 索引后同一查询 13.84 → 9.44 ms（**-32%**），但相对 265ms 的总成本只有 1.7% 收益，**不是优先项**。

### 3.2 渲染与 RSC 序列化占 95%

- 公开页把 240 条书签 + 60 个标签一起传给**客户端组件** `HomeBody`，同一份数据既出现在 SSR HTML 里，又要出现在 RSC payload 里供 hydration → 894KB 响应、265ms CPU；
- 对比：`/user/bookmark/list` 只下发 18KB 的客户端 shell，单请求 CPU 仅 56.7ms；
- 每个页面还要额外渲染导航栏（含全部标签）与布局数据，形成约 **200KB 的固定开销**（60 条时首页仍有 306KB）。

### 3.3 单线程饱和

并发梯度（首页，60 条）：

| 并发 | RPS | p50 (ms) | CPU 核 |
| --- | --- | --- | --- |
| 1 | 9.5 | 101.6 | 0.99 |
| 2 | 10.1 | 193.0 | 1.00 |
| 4 | 11.6 | 322.8 | 1.05 |
| 8 | 12.9 | 566.5 | 1.15 |
| 16 | 9.2 | 1750.7 | 1.05 |

并发 1 时 CPU 就接近 1 核 —— 请求本身是 CPU 密集的，加并发只能排队拉高 p50，**吞吐上限 ≈ 1 / 单请求 CPU**。这就是「扩副本而不是扩并发」的依据。

## 4. 已落地的优化

| # | 改动 | 位置 | 依据 |
| --- | --- | --- | --- |
| 1 | 首页默认页大小 240 → **60** | [`app.config.ts`](../app.config.ts) `DEFAULT_BOOKMARK_PAGESIZE = 3 * 4 * 5` | 渲染成本与条目数近似线性 |
| 2 | 标签页默认页大小 600 → **120** | [`app.config.ts`](../app.config.ts) `DEFAULT_PUBLIC_TAG_PAGESIZE = 3 * 4 * 10` | 同上，且标签页单页 927KB |
| 3 | `/tags` 改为路由层重定向 | [`next.config.js`](../next.config.js) `redirects()` | 避免为一次跳转付出整页 SSR |

页大小仍是 12 的倍数（栅格 3/4 列适配），「加载更多」按同样的页大小翻页。

## 6. 容量模型

以优化后的数据估算（单副本、1 核上限）：

| 页面 | 单请求 CPU | 理论 RPS/副本 | 备注 |
| --- | --- | --- | --- |
| `/api/health` | 2.4 ms | ~400 | 不碰 DB |
| `/api/health/deep` | 2.9 ms | ~340 | 含一次 DB 查询 |
| 首页 | 90~114 ms | 9~11 | 与实测一致 |
| 标签详情 | 169~185 ms | 5~6 | 条目更多 |
| 用户列表 | ~54 ms | ~18 | 客户端渲染 shell |

按 3 副本 + 负载均衡估算：首页约 **27~33 RPS**、可支撑约 **2,300~2,800 次/分钟** 的页面浏览；若再叠加 P1 中的缓存与组件拆分，单副本预期还能提升 40%~60%。

## 7. 后续优化建议

| 优先级 | 事项 | 预期收益 | 成本 |
| --- | --- | --- | --- |
| P0（已做） | 页大小下调 + 路由层重定向 | 首页 -60% CPU，`/tags` 80× | 已完成 |

## 8. 复现

```bash
# 1) 准备数据（会清空 perf.db 中的业务数据）
cp sqlite.db perf.db
DB_CONNECTION_URL=file:./perf.db node bench/seed.mjs

# 2) 起服务（生产构建）
pnpm build
HOSTNAME=127.0.0.1 AUTH_URL=http://127.0.0.1:3500 \
  DB_DRIVER=sqlite DB_CONNECTION_URL=file:./perf.db AUTH_SECRET=perf \
  npx next start -p 3500

# 3) 压测
node bench/run.mjs --server-pid $(pgrep -f next-server | head -1)
node bench/run.mjs --mode ramp --connections 1,2,4,8,16 --only /
```

## 9. 局限

1. **同机压测**：客户端与服务端抢同一组 4 vCPU，绝对 RPS 偏低，延迟含客户端排队；
2. **SQLite 单文件**：未覆盖 PostgreSQL / Turso 的连接池与网络开销；
3. **无反向代理与 TLS**：真实部署多一层 Caddy/Nginx（可再吃 20%~40% CPU，建议压测时把代理也纳入）；
4. **只压了读路径**：服务端 Action、AI 分析、图标抓取等写/外部依赖路径未覆盖；
5. 数据为合成数据（60 标签 × 5000 书签，每条 3 标签），与真实内容分布不同。
