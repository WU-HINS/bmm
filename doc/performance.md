# 性能压测报告

> 被测版本：`7103806`（含健康检查端点）→ 本文优化后基线
> 压测时间：单机闭环压测，3 轮取中位数
> 复现：`node bench/seed.mjs` + `node bench/run.mjs --server-pid <pid>`

---

## 0. 结论

1. **公开页面的瓶颈是渲染与序列化，不是数据库**：优化前首页单请求 CPU 265ms，其中数据库只占 13.8ms（5%）。
2. **两轮优化后首页单请求 CPU 265ms → 52.7ms（-80%）**，单副本吞吐 4.3 → **19~24 RPS（约 4.4~5.6×）**，响应体积 894KB → 275KB（-69%）。
3. **三个最大的杠杆**：① 首屏条目数 240 → 60；② 卡片标记瘦身（标签胶囊/悬浮提示改原生写法，单卡 2.8KB → 约 1.7KB）；③ 公开页读路径走进程内 TTL 缓存 + 写路径失效。
4. **Node 单进程是硬顶**：所有场景 CPU 占用稳定在 ~1.0~1.15 核。**扩容靠多副本**，加并发只会拉高 p50。
5. **路由级重定向的代价被严重低估**：`/tags` 从页面内 `redirect()` 改到 `next.config redirects()` 后 **31.8 → 1555~2554 RPS**。
6. 用户空间页面本来就轻（45~57ms CPU/req，20~27 RPS），不受本轮优化影响。

## 3. 瓶颈定位

### 3.1 数据库只占 5%

在 perf.db 上直接调用 controller（不经过 HTTP）：

| 调用 | 平均耗时 |
| --- | --- |
| `PublicTagController.getAll()`（60 个标签） | ~0.00 ms |
| `PublicBookmarkController.total()` | 0.23 ms |
| `findMany()` 240 条 + 关联标签 | **13.84 ms** |
| `findMany({ limit: 60 })` | 4.79 ms |
| `findMany({ limit: 24 })` | 3.71 ms |

查询计划（`ORDER BY updatedAt DESC LIMIT 240`）：

```
SCAN publicBookmarks
USE TEMP B-TREE FOR ORDER BY
```

建 `updatedAt` 索引后同一查询 13.84 → 9.44 ms（**-32%**），但相对 265ms 的总成本只有 1.7% 收益，**不是优先项**。

### 3.2 渲染与 RSC 序列化占 95%

- 公开页把 240 条书签 + 60 个标签一起传给**客户端组件** `HomeBody`，同一份数据既出现在 SSR HTML 里，又要出现在 RSC payload 里供 hydration → 894KB 响应、265ms CPU；
- 对比：`/user/bookmark/list` 只下发 18KB 的客户端 shell，单请求 CPU 仅 56.7ms；
- 每个页面还要额外渲染导航栏（含全部标签）与布局数据，形成约 **200KB 的固定开销**（60 条时首页仍有 306KB）。

### 3.3 单线程饱和

并发梯度（首页，60 条）：

| 并发 | RPS | p50 (ms) | CPU 核 |
| --- | --- | --- | --- |
| 1 | 9.5 | 101.6 | 0.99 |
| 2 | 10.1 | 193.0 | 1.00 |
| 4 | 11.6 | 322.8 | 1.05 |
| 8 | 12.9 | 566.5 | 1.15 |
| 16 | 9.2 | 1750.7 | 1.05 |

并发 1 时 CPU 就接近 1 核 —— 请求本身是 CPU 密集的，加并发只能排队拉高 p50，**吞吐上限 ≈ 1 / 单请求 CPU**。这就是「扩副本而不是扩并发」的依据。

| 优先级 | 事项 | 状态 | 实测收益 |
| --- | --- | --- | --- |
| P0 | 首屏条目数下调（240/600 → 60/120） | ✅ 已做 | 首页 CPU -57%~-66% |
| P0 | `/tags` 改路由层重定向 | ✅ 已做 | 31.8 → 1555~2554 RPS |
| P0 | 卡片标记瘦身（Chip/Tooltip → 原生标签） | ✅ 已做 | 单卡 2.8KB → 约 1.7KB，首页再 -42% CPU |
| P0 | 公开页读路径 TTL 缓存 + 写失效 | ✅ 已做 | 首页 90~114 → 52.7ms |
| P0 | 静态资源 `Cache-Control` | ✅ 已做 | 重复访问省流量 |
| P1 | `updatedAt` 索引（公共 + 用户书签） | ✅ 已做 | 查询 -32%（13.84 → 9.44ms） |
| P1 | 整页路由缓存 / ISR | ⏸ 见下方说明 | 预估 10×+ |
| P2 | 列表改为纯服务端组件渲染 | ⏸ 收益有限 | 实测 HTML 占 82%、RSC 仅 18% |
| P2 | 游标分页（消除 OFFSET） | ⏸ | 深翻页收益 |
| P3 | 写入路径（新增书签 / AI 分析 / 抓取）压测 | ⏸ | — |

### 为什么没有直接上「整页缓存 / ISR」

这是剩下最大的杠杆（缓存命中时代价接近静态文件，预估 10×+），但当前有两个硬阻塞：

1. **根布局调用 `auth()`**：[`src/app/layout.tsx`](../src/app/layout.tsx) 为了给 `SessionProvider` 传入初始会话，让所有页面都变成动态渲染，整页缓存无从谈起；
2. **构建期 DB 为空**：CI/Docker 构建时数据库是空的，`/` 会按「0 条书签」预渲染成 `/welcome` 的重定向页，ISR 首次命中会把这个错误结果发给用户。

要落地需要三步改造（本轮未做，避免把性能优化变成架构迁移）：

- 把会话改为纯客户端获取（`<SessionProvider>` 不传 session，配合导航栏骨架屏），根布局不再调用 `auth()`；
- 公开页加 `export const revalidate = 30`，并在管理端写操作里 `revalidatePath('/')`、`revalidatePath('/tags/[slug]', 'page')`；
- 构建期用空库渲染时不要重定向（渲染空态即可），或给静态生成单独的构建环境变量。

另外，实测 HTML 占响应的 82%、RSC payload 仅 18%，所以「把列表改成服务端组件」的收益只有 10%~15%（省的是 hydration 数据与客户端 JS），不如整页缓存划算。

## 9. 内存占用

测量方式：`bench/memory.mjs` 每 500ms 采样 `/proc/<pid>/status` 的 `VmRSS`（当前常驻）与 `VmHWM`（历史峰值），服务端以 `NODE_OPTIONS=--max-old-space-size=512` 运行。

| 阶段 | 请求数 | RPS | RSS 均值 | RSS 峰值 | HWM 峰值 |
| --- | --- | --- | --- | --- | --- |
| 启动后（未预热） | - | - | 136 MB | 136 MB | 136 MB |
| 预热后空闲 | - | - | 165~195 MB | 195 MB | 195 MB |
| `/api/health` 16 并发 | 8,077 | 403.3 | 228 MB | 238 MB | 241 MB |
| 首页 8 并发 | 438 | 21.7 | 268 MB | 279 MB | 280 MB |
| 首页 **64 并发突发** 10s | 256 | 22.4 | 316 MB | **358 MB** | 357 MB |

结论：

- **单副本稳定在 250~290 MB**，突发峰值 **~360 MB**；吞吐提升不额外增加稳态内存（RSS 主要由 Next 运行时 + V8 堆决定）。
- **无泄漏**：首页连续 6 轮（每轮 10s、8 并发）结束后 RSS 从 274.0 → 277.1 MB，仅 **+3.2 MB**，属于堆碎片/惰性回收，不随轮次线性增长。
- 内存主要由「并发中的 SSR 渲染」驱动：8 并发 → +28 MB，64 并发 → +110 MB。

### 压测暴露并修复的问题：缓存长尾 key

第一版 TTL 缓存（`findMany` 按查询参数做 key）没有限容，被压测直接打爆：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 1500 个不同 `?keyword=` 请求 | RSS **+72 MB**，且 TTL 过期后不回落 | RSS **+7 MB**（GC 内即可回收） |

修复（[lib/ttl-cache.ts](../src/lib/ttl-cache.ts)）：

1. **长尾不入缓存**：`findMany` 只在没有 `keyword` 时缓存（首页、标签页等固定参数），关键词搜索直接查库；
2. **限容**：`MAX_ENTRIES = 128`，超限时先清扫过期项、再按插入顺序淘汰最旧条目；
3. **过期清扫**：每 30s 扫一次过期 key，避免「只写不读」的 key 永久驻留。

### 容器资源建议

| 资源 | 建议值 | 依据 |
| --- | --- | --- |
| requests.memory | 256 Mi | 稳态 250~290 MB 的下限侧 |
| limits.memory | 512 Mi | 突发峰值 358 MB + 余量 |
| `NODE_OPTIONS` | `--max-old-space-size=384` | 让 V8 在容器 OOM 之前先自己回收 |
| requests.cpu / limits.cpu | 500m ~ 1000m | 单副本吃满 1 核（见第 3.3 节） |

3 副本 × 512 Mi ≈ 1.5 GiB，可在 2 GiB 节点上跑 3 副本。

## 10. 局限

1. **同机压测**：客户端与服务端抢同一组 4 vCPU，绝对 RPS 偏低，延迟含客户端排队；
2. **SQLite 单文件**：未覆盖 PostgreSQL / Turso 的连接池与网络开销；
3. **无反向代理与 TLS**：真实部署多一层 Caddy/Nginx（可再吃 20%~40% CPU，建议压测时把代理也纳入）；
4. **只压了读路径**：服务端 Action、AI 分析、图标抓取等写/外部依赖路径未覆盖；
5. 数据为合成数据（60 标签 × 5000 书签，每条 3 标签），与真实内容分布不同。
